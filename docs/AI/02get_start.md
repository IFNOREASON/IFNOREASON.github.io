# 基础概念

## 大模型
>   大型语言模型（英语：large language model，LLM），也称大语言模型，简称大模型，是一种基于人工神经网络的语言模型。其名称中的“大型”指模型具有庞大的参数量（通常在数十亿以上，如GPT-3含1750亿参数）以及巨大的训练数据规模。大语言模型通常采用自监督机器学习，能够在海量无标注的文本上训练。大语言模型专为自然语言处理任务而设计，尤其是语言生成。其中包含Gemini和GPT-4o在内的部分模型具有多模态功能，能够同时处理文字、图片、音频和视频等不同输入形式。大多数LLM采用了生成式预训练变换器(GPT) ，它们为ChatGPT、Gemini和Claude等聊天机器人提供了核心功能。这些模型能够预测人类语言语料库中固有的句法、语义和本体信息[3]，且展示出相当多训练期间“记住”的关于世界的常识。但它们也继承了训练数据中存在的误差和偏差。

- 1.2 "大"的体现
- ✅ **参数规模大**（百亿、千亿甚至万亿级）
- ✅ **架构规模大**
- ✅ **训练数据大**
- ✅ **算力需求大**

## 大模型应用开发

>   大模型应用开发是指将基础大模型的能力转化为具体业务解决方案的工程实践过程。与大模型开发（聚焦于构建基础模型能力，技术定位类似“操作系统”）不同，大模型应用开发的技术定位更接近“应用软件”，其核心目标是通过一系列工程技术手段，使通用大模型适配特定场景需求。

# 大模型核心概念解析

以下是大模型应用开发中必须吃透的 **N 个核心概念**，它们直接决定了 API 调用的成本、效果和稳定性。


## 一、Token（词元）—— AI 的“计量单位”与“硬通货”

### 1. 定义
Token 是大模型处理文本时的**最小基本单元**。大模型不认识完整的单词或汉字，它会将输入的文本拆解为一个个 Token 进行数学运算。

### 2. 拆分规则（中英文差异）
| 语言 | 对应规则 | 示例 |
| :--- | :--- | :--- |
| **英文** | 1 个 Token ≈ 0.75 个单词（约 4 个字符） | "Hello world" ≈ 2 Tokens |
| **中文** | 1 个常用汉字 ≈ 1 个 Token | "你好世界" = 4 Tokens（复杂生僻字可能占 2-3 个） |
| **代码/特殊符号** | 空格、换行、标点均算作独立 Token | 空格也是钱！ |

### 3. 对开发者的致命影响
- **💰 计费标准**：所有商业 API（OpenAI、DeepSeek 等）**按输入 Token 数 + 输出 Token 数**累加计费。
- **📏 物理天花板**：模型存在 **上下文窗口**（如 128K、1M），指的就是输入+输出总 Token 数不能超限。
- **⚙️ 实操避坑**：写提示词要惜字如金；处理长文档必须做 **Chunking（切片）**，否则不仅费用飙升，还会直接报错。


## 二、提示词（Prompt）—— 你给 AI 的“指令文本”

### 1. 定义
就是用户输入给大模型的**那一串自然语言文本**。但在应用开发中，它不是简单的“问问题”，而是由多层指令组合而成的结构化文本。

### 2. 开发视角的两大组成部分
| 类型 | 作用 | 示例 |
| :--- | :--- | :--- |
| **System Prompt（系统提示词）** | 设定 AI 的“人设”、底层规则和输出限制（通常隐藏在前端背后）。 | “你是一名资深 Java 工程师，只输出代码，不要解释。” |
| **User Prompt（用户提示词）** | 当前用户这一次具体想问的内容或任务。 | “请用冒泡排序实现一个数组升序排列。” |

### 3. 工程核心
**提示词工程（Prompt Engineering）** 是应用开发中性价比最高的调优手段。通过结构化的指令（角色+任务+步骤+格式约束），不需要重新训练模型，就能将准确率从 40% 提升至 90%。


## 三、上下文（Context）—— AI 的“当前工作记忆区”

### 1. 定义
指模型在**生成当前回答这一刻**，所能参考到的全部背景信息。 
⚠️ **注意**：大模型本身没有长期记忆！每次调用都是“失忆”状态。

### 2. 两个层面的含义
| 层面 | 概念 | 说明 |
| :--- | :--- | :--- |
| **容量层面** | **上下文窗口** | 硬件的物理限制（Token 总数上限）。 |
| **内容层面** | **上下文信息** | 实际包含的内容：系统提示词 + 历史多轮对话 + RAG 检索回来的外部文档片段。 |

### 3. 开发实战逻辑
为了维持多轮对话，开发者必须在代码中手动维护一个 **Memory（记忆）列表**，每次请求前把 `System Prompt + 历史摘要 + 当前问题` 重新拼装起来，塞进上下文窗口中。这就是 RAG（检索增强生成）技术的核心由来——因为窗口有限，只能通过向量检索把最相关的文档片段“塞”进去。


## 四、温度（Temperature）—— 控制“创造力”与“稳定性”

### 1. 定义
一个调节模型**输出随机性**的超参数。它控制模型在生成下一个 Token 时，对候选词概率分布的“锐化”或“平滑”程度。

### 2. 取值范围与效果
| 数值范围 | 表现效果 | 适用场景 |
| :--- | :--- | :--- |
| **0.0 ~ 0.3（低）** | **极度稳定、保守**。模型几乎总是选概率最高的词，回答确定性强，但略显死板。 | **数学计算、代码生成、数据提取、事实问答**（需要高精度的场景）。 |
| **0.7 ~ 1.0（中）** | **平衡且自然**。有一定随机性，但不会脱离逻辑。 | **通用对话、文案撰写、翻译**（大多数默认值）。 |
| **1.0 ~ 2.0（高）** | **极具创造力**。会尝试更多低概率词汇，输出天马行空，但可能出现胡言乱语或逻辑断裂。 | **头脑风暴、诗歌创作、创意故事**（需谨慎使用）。 |


## 五、Top_p（核采样）—— 控制“候选词池”的大小

### 1. 定义
一种**动态截断采样**策略。模型会按概率从高到低对词汇进行排序，累加概率直到总和达到 `p` 值（0~1之间），只在这个累积概率覆盖的“小池子”里随机选词。

### 2. 直观理解
- **Top_p = 0.1**：只从累积概率前 10% 的“最靠谱候选词”里选，几乎不会出错。
- **Top_p = 0.9**：保留累积概率 90% 的候选词池（可能包含几十个词），多样性明显增加。
- **Top_p = 1.0**：不考虑限制，从模型全量词汇表中选（默认值，相当于关闭过滤）。

### 3. ⚠️ 开发者黄金法则
`Temperature` 和 `Top_p` **不建议同时调整**！ 
官方推荐做法是：**固定其中一个不变，只微调另一个**。

- **习惯做法 A**：固定 `Top_p = 0.9`，只调整 `Temperature`（更方便直观）。
- **习惯做法 B**：固定 `Temperature = 1.0`，只调整 `Top_p`。

## 六、Chat Completions API 与 Responses API 完全解析

### 1、核心定位与演进

**Chat Completions API** 和 **Responses API** 是目前构建大模型应用时最核心的两个接口。前者是上一代“对话”接口，后者是 OpenAI 于 2025 年 3 月推出的新一代“智能体”接口。**官方明确建议，所有新项目应优先使用 Responses API。**

#### 💡 直观比喻

- **Chat Completions API** = **收发室**：你寄一封信（提问），它送一次回信（回答）。信的内容和上下文需要你自己保管。
- **Responses API** = **私人助理**：你把任务交给它，它会自己思考、查资料、用工具，最后把完整结果交给你，并且能记住之前聊过什么。

---

### 2、核心差异深度对比

#### 🔹 差异一：状态管理（最根本的区别）

| API | 状态管理 | 说明 |
| :--- | :--- | :--- |
| **Chat Completions** | **无状态** | 模型不记忆任何历史对话。每次请求必须将**完整对话历史**（系统提示、用户问题、历史回复等）全部塞入 `messages` 数组。对话越长，Token 消耗越多，成本越高。 |
| **Responses API** | **有状态** | 模型可在服务端维护对话状态。只需传入 `previous_response_id` 引用之前的对话，无需重复发送历史记录，简化代码、降低成本。 |

#### 🔹 差异二：输入与输出格式

##### 请求格式

- **Chat Completions**：使用 `messages` 数组，包含 `role`（角色）和 `content`（内容）。
- **Responses API**：使用更简洁的 `input` 字段，并用独立的 `instructions` 字段替代系统提示词（System Prompt）。

##### 响应格式

- **Chat Completions**：返回单一 `chat.completion` 对象，回复内容在 `choices[0].message.content` 中。
- **Responses API**：返回 `response` 对象，包含 `output` 数组，可包含多种类型的“条目（Items）”：
  - `message`：最终回复文本
  - `reasoning`：模型的内部推理过程
  - `function_call`：模型请求调用工具
  - `function_call_output`：工具执行后的结果

#### 🔹 差异三：工具（Tools）与执行能力

这是 **Responses API 最强大的升级点**。

| API | 工具支持 | 工具执行方式 |
| :--- | :--- | :--- |
| **Chat Completions** | 主要支持自定义 `function` 工具 | 模型只返回工具调用请求，**真正的执行逻辑（如调用天气 API、搜索数据库）需在客户端代码中完成**。 |
| **Responses API** | 自定义函数 + **多种内置托管工具** | 内置工具由 OpenAI 平台**自动执行**，无需编写复杂的工具调用循环逻辑（Agent Loop）。 |

**内置托管工具一览**：
- `web_search`：网络搜索
- `file_search`：文件搜索
- `computer_use`：计算机使用
- `code_interpreter`：代码解释器
- `remote MCPs`：远程 MCP 服务

在一次 API 请求中，模型可自主完成“思考 → 调用工具 → 基于结果再思考”的完整循环。

#### 🔹 差异四：性能与成本

- **成本节约**：因更好的缓存利用，Responses API 在内部测试中可带来 **40% ~ 80%** 的成本节约。
- **性能表现**：在某些基准测试（如 SWE-bench）中表现更优。
- **推理过程可见**：Responses API 可返回推理过程（`reasoning` items），便于调试和理解模型行为。
- **面向未来**：Responses API 专为 GPT-5 等新一代推理模型设计，能更好发挥其潜力。

---

### 3、快速对比一览表

| 对比维度 | **Chat Completions API** | **Responses API** |
| :--- | :--- | :--- |
| **设计哲学** | 无状态、单轮对话补全 | 有状态、多轮智能体循环 |
| **请求端点** | `POST /v1/chat/completions` | `POST /v1/responses` |
| **输入格式** | `messages` 数组（含完整历史） | `input` + `previous_response_id` |
| **系统提示** | 作为 `messages` 中的一条 | 独立的 `instructions` 字段 |
| **状态管理** | ❌ 无状态，客户端维护 | ✅ 有状态，服务端维护 |
| **内置工具** | 仅 `function` | `function`、`web_search`、`file_search` 等 |
| **工具执行** | 客户端自行执行 | 平台自动执行内置工具 |
| **响应内容** | 单一回复文本 | 可包含推理、工具调用、回复等多条目 |
| **当前状态** | 现行标准，长期支持 | **新项目官方推荐** |

## 七、流式输出与 SSE（Server-Sent Events）概念解析

在大模型应用开发中，流式输出是提升用户体验的核心技术之一。而 **SSE（Server-Sent Events，服务器发送事件）** 正是目前实现大模型流式输出的**事实标准协议**。

---

### 1、什么是流式输出？

流式输出是指大模型在生成回答时，**逐字、逐词或逐块地实时将内容推送给客户端**，而不是等待整个回答生成完毕后再一次性返回。

#### 💡 直观对比

- **非流式（全量输出）**：用户提问后，界面显示“加载中...”转圈 5~10 秒，然后突然一次性蹦出几百字的长文。
- **流式输出**：用户提问后，约 0.5~1 秒就开始出现第一个字，随后文字像打字机一样一个字一个字地“蹦”出来，直至生成完毕。

#### 🎯 为什么大模型必须用流式输出？

| 原因 | 说明 |
| :--- | :--- |
| **极速感知（TTFT 优化）** | 大模型生成 500 字可能需要 10 秒，但首 Token 延迟（TTFT）通常仅需几百毫秒。流式输出让用户立刻知道“模型在干活了”，大幅降低焦虑感。 |
| **防止超时中断** | 全量生成耗时较长，容易触发网关或浏览器的超时限制（如 Nginx 默认 60 秒）。流式输出通过持续发送数据包来“刷新”超时计时器，保持连接活跃。 |
| **思维链（CoT）可视化** | 当模型进行复杂推理时，流式输出可实时展示其推理步骤，增强可解释性和用户信任感。 |

---

### 2、什么是 SSE（Server-Sent Events）？

SSE 是一种基于 **HTTP 协议** 的轻量级服务器推送技术。它允许服务器在建立一次连接后，**持续向客户端单向推送** 数据流。

#### 🔧 技术本质

- **协议**：标准 HTTP/1.1 或 HTTP/2
- **MIME 类型**：`Content-Type: text/event-stream`
- **连接特性**：保持长连接（Keep-Alive），直到服务器主动关闭或超时
- **方向性**：**单向**（仅服务器 → 客户端）

#### 📡 SSE 数据格式示例

SSE 协议规定数据以 `data:` 开头，并以两个换行符 `\n\n` 结尾：

```text
data: {"id":"1","content":"你"}

data: {"id":"2","content":"好"}

data: {"id":"3","content":"世"}

data: {"id":"4","content":"界"}

data: [DONE]
```

> 前端通过 `EventSource` API 或 `fetch` + `ReadableStream` 来解析这些数据块。

---

### 3、SSE vs WebSocket vs 轮询（横向对比）

对于 AI 应用开发者而言，理解这三种技术的区别至关重要：

| 对比维度 | **SSE（服务器发送事件）** | **WebSocket** | **长轮询（Long Polling）** |
| :--- | :--- | :--- | :--- |
| **通信方向** | **单向**（服务器 → 客户端） | **全双工**（双向实时） | 单向（客户端发起，服务器延迟响应） |
| **协议** | HTTP（标准协议） | WS / WSS（独立协议） | HTTP |
| **自动重连** | ✅ **内置支持**（断线自动恢复） | ❌ 需手动实现 | ❌ 需手动实现 |
| **二进制数据** | ❌ 仅文本（但可 Base64 编码） | ✅ 原生支持 | ❌ 仅文本 |
| **复杂度** | **极低**（仅需设置响应头） | 较高（需握手协议、心跳保活） | 低（但浪费资源） |
| **适用场景** | **AI 流式文本输出**、实时通知、推送 | 实时聊天、在线游戏、协同编辑 | 老旧系统兼容方案 |

#### ✅ 为什么大模型流式输出普遍采用 SSE，而不是 WebSocket？

1.  **技术栈简单**：SSE 直接复用现有 HTTP 基础设施，无需像 WebSocket 那样进行协议升级（Upgrade）和额外的端口管理。
2.  **自动重连机制**：SSE 内置断线重连功能，对于网络不稳定的移动端尤其友好。
3.  **足够使用**：大模型流式输出的场景是“服务器不断吐字给客户端”，属于**单向数据流**，完全不需要客户端向服务器发消息的双向能力（用户发新问题会单独发起新的 HTTP 请求）。
4.  **防火墙友好**：标准 80/443 端口通行无阻，而 WebSocket 在某些企业防火墙下可能被拦截。

### 4、在代码中如何实现（实战速览）

#### 🖥️ 后端（以 Python FastAPI 为例）

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import asyncio

app = FastAPI()

async def generate_text():
    # 模拟大模型逐字生成
    for char in "你好，世界！这是一个流式输出的例子。":
        yield f"data: {char}\n\n"  # SSE 标准格式
        await asyncio.sleep(0.1)  # 模拟模型推理延迟
    yield "data: [DONE]\n\n"

@app.get("/stream")
async def stream_chat():
    return StreamingResponse(
        generate_text(), 
        media_type="text/event-stream"  # 关键：必须指定此 MIME
    )
```

#### 🎨 前端（JavaScript 原生 API）

```javascript
// 方式一：EventSource（最简方案，仅支持 GET）
const eventSource = new EventSource('/stream');
eventSource.onmessage = (event) => {
    if (event.data === '[DONE]') {
        eventSource.close();
        return;
    }
    console.log(event.data); // 逐字打印
};

// 方式二：Fetch + ReadableStream（支持 POST，更灵活）
const response = await fetch('/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ messages: [...] })
});
const reader = response.body.getReader();
const decoder = new TextDecoder();
while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    const chunk = decoder.decode(value);
    // 解析 chunk 中的 SSE 数据...
}
```

### 5、流式输出的“隐藏功能”（进阶必知）

在大模型应用开发中，SSE 流不仅用于传文本，还常用于传 **结构化控制信号**：

| 信号类型 | SSE 数据示例 | 用途 |
| :--- | :--- | :--- |
| **文本块** | `data: {"type":"text","content":"你好"}` | 逐字渲染给用户 |
| **推理过程** | `data: {"type":"reasoning","content":"首先，我需要..."}` | 展示“思维链”（DeepSeek-R1 等推理模型专有） |
| **工具调用** | `data: {"type":"tool_call","name":"search_web"}` | 前端显示“正在搜索...”的状态动画 |
| **结束标志** | `data: [DONE]` | 通知前端关闭连接并启用“复制/点赞”按钮 |

## 八、函数调用 / 工具调用概念解析

---

### 1、什么是函数调用？

函数调用（Function Calling）是大模型连接外部世界的关键机制。它让大模型不仅能“聊天”，还能输出**结构化的指令**，由你的代码去执行实际操作（查天气、发邮件、查数据库），最后将结果返回给模型生成自然语言回复。

> **一句话理解**：模型负责“决策”（输出JSON指令），你的代码负责“动手”（执行具体操作）。


---

### 2、核心工作流程（三步走）

**第一步：注册工具** —— 客户端在请求中传入 `tools` 参数，告知模型有哪些工具可用（名称、描述、参数格式）。

**第二步：模型决策** —— 模型判断是否需要调用工具。若需要，返回**结构化JSON**（填充好参数），而非直接答案。

**第三步：执行与回传** —— 你的代码执行真实操作，将结果回传给模型，模型再生成最终自然语言回复。

---

### 3、关键概念速览

| 概念 | 说明 |
| :--- | :--- |
| **Tool Choice** | 控制调用策略：`"auto"`（模型自主判断）、`"none"`（禁止调用）、`{"type":"function","function":{"name":"xxx"}}`（强制调用指定工具） |
| **并行调用** | 一次返回多个工具调用，可并发执行，大幅降低耗时 |
| **描述越详细，调用越准** | 工具和参数的 `description` 越清晰，模型越能在正确时机触发调用 |

### 4、两代API中的差异

| 对比维度 | **Chat Completions API** | **Responses API** |
| :--- | :--- | :--- |
| 自定义函数 | 需手动实现执行逻辑 | 需手动实现执行逻辑 |
| 内置工具 | ❌ 不支持 | ✅ 支持 `web_search`、`file_search` 等托管工具，由平台自动执行 |
| 结果回传格式 | `role: "tool"` | `function_call_output` 条目 |
