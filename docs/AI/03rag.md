# RAG（检索增强生成）技术知识库


## 一、检索增强生成（RAG）概述

### 1.1 LLM 的缺陷分析

大语言模型虽然在通用任务上表现出色，但仍存在以下关键缺陷：

| 缺陷类型 | 具体表现 |
| :--- | :--- |
| **知识时效性局限** | 模型训练数据截止于特定时间点，无法获取最新信息 |
| **幻觉问题** | 模型在不确定时会“编造”答案，尤其在专业领域表现突出 |
| **缺乏专业深度** | 通用模型在垂直行业（医疗、法律、金融）的精度不足 |
| **无法追溯来源** | 模型无法告知用户答案的具体出处，降低可信度 |
| **长文本信息遗忘** | 在处理超长文档时，中间部分信息容易被“忽略” |

### 1.2 RAG 的定义

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种将**信息检索**与**大语言模型生成**相结合的技术范式。其核心思想是：在模型生成答案之前，先从外部知识库中检索与问题相关的文档片段，将这些片段作为“上下文背景”注入到Prompt中，让模型基于检索到的信息生成更准确、更可靠的回答。

> **一句话理解**：RAG = 检索相关文档 + 大模型基于文档生成答案，相当于给模型配备了一个可随时翻阅的“外部知识库”。

### 1.3 RAG 应用场景分析

| 场景类别 | 典型应用 |
| :--- | :--- |
| **智能客服** | 企业FAQ问答、售后技术支持、产品咨询 |
| **知识库问答** | 企业内部文档检索、法律文书查询、医疗知识库 |
| **教育辅导** | 智能教材问答、个性化学习助手 |
| **金融分析** | 财报解析、研报查询、市场信息整合 |
| **代码辅助** | 代码文档检索、API查询、技术栈问答 |
| **内容创作** | 基于事实数据的报告生成、新闻摘要 |


## 二、RAG 的三大范式

### 2.1 Naive RAG（朴素 RAG）

最早的RAG实现方式，流程简单直观：

1. 将文档切分成块（Chunking）
2. 将文本块向量化存入向量数据库
3. 用户提问时，检索最相似的Top-K文本块
4. 将检索结果拼接到Prompt中，让模型生成答案

**优点**：实现简单，快速上手。
**缺点**：检索精度有限，召回质量不高，生成结果常包含冗余信息。

### 2.2 Advanced RAG（进阶 RAG）

在Naive RAG基础上引入了更多优化技术：

- **索引优化**：文档切片策略优化、多级索引
- **检索前优化**：查询改写、HyDE（假设文档嵌入）
- **检索后优化**：重排序（Reranker）、上下文压缩、结果过滤
- **融合检索**：混合检索（语义+关键词）

**优点**：检索精度显著提升，回答质量更高。
**缺点**：系统复杂度增加，需要更多工程调优。

### 2.3 Modular RAG（模块化 RAG）

将RAG流程拆解为独立的可插拔模块，支持灵活组合和编排：

| 核心模块 | 功能说明 |
| :--- | :--- |
| **查询引擎** | 查询理解、改写、扩展 |
| **检索器** | 多路召回（向量检索、关键词检索、图检索） |
| **融合器** | 多路结果融合与重排序 |
| **生成器** | 基于增强上下文的答案生成 |
| **评估器** | 答案质量评估与反馈 |

**优点**：灵活性高，各模块可独立优化和替换，适应复杂场景。
**缺点**：架构设计门槛较高。需要注意的是，**Modular RAG更接近一种架构思想**，而非单一技术方案。


## 三、RAG 的三大部件

| 部件 | 英文 | 核心职责 |
| :--- | :--- | :--- |
| **检索器** | Retriever | 从知识库中快速检索与问题最相关的文档片段 |
| **生成器** | Generator | 基于检索到的上下文生成最终的自然语言回答 |
| **增强方法** | Augmentation Method | 定义如何将检索结果与原始问题结合（包括注入策略、提示词模板设计等） |


## 四、Naive RAG Pipeline 完整流程

### 第一阶段：知识库构建

#### 4.1 文档加载和分块

**文档加载**：从各类数据源（PDF、Word、HTML、数据库等）读取原始文档，统一转化为纯文本格式。

**分块方案详解（Chunking Strategy）**：

| 分块方式 | 说明 | 适用场景 |
| :--- | :--- | :--- |
| **固定大小分块** | 按固定Token数或字符数切分（如512 Tokens），可设置重叠区域 | 通用场景，最简单 |
| **按句子分块** | 以句子边界（句号、问号、感叹号）为分割点 | 追求语义完整性 |
| **按段落分块** | 以段落换行为分割点 | 文档结构清晰时 |
| **语义分块** | 利用Embedding相似度自动识别语义边界 | 追求最优语义一致性 |
| **递归分块** | 按层级依次切分（段落→句子→固定大小回退） | 综合最优，LangChain默认方案 |

**关键参数**：
- **Chunk Size（块大小）** ：通常256-1024 Tokens
- **Overlap（重叠区域）** ：建议为Chunk Size的10-20%，保证跨块上下文不丢失

### 第二阶段：Embeddings 向量化

#### 4.2 向量化的意义

将文本转换为高维向量（通常768-4096维），使计算机能计算文本之间的**语义相似度**。语义相近的文本在向量空间中距离更近。

#### 4.3 向量化实践

##### 主流 Embedding 模型对比

| 模型名称 | 提供商 | 向量维度 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **OpenAI Embedding** | OpenAI | 1536（text-embedding-ada-002）| 通用英文场景，生态成熟 |
| **百度文心 Embedding-V1** | 百度 | 1024 | 中文场景，百度云生态 |
| **GLM Embedding** | 智谱AI | 1024 | 中文场景，开源友好 |
| **bge-large-zh-v1.5** | BAAI（北京智源） | 1024 | 中文最佳性能之一，开源免费 |

> **选型建议**：中文场景优先选择 `bge-large-zh-v1.5` 或 `GLM Embedding`；多语言场景考虑OpenAI系列；企业私有化部署优先选择开源模型。

#### 4.4 向量相似度算法

| 算法 | 英文 | 公式逻辑 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **余弦距离** | Cosine Similarity | 计算两向量夹角余弦值（范围-1~1），值越大越相似 | **最常用**，对向量模长不敏感 |
| **点积** | Inner Product (IP) | 计算两向量对应元素乘积之和 | 向量已归一化时等价于余弦 |
| **欧式距离** | L2 Distance | 计算两向量的直线距离，距离越小越相似 | 对向量模长敏感的场景 |

> **实践建议**：多数向量数据库默认使用**余弦距离**，效果稳定，为首选方案。

### 第三阶段：向量数据库

#### 4.5 向量数据库的作用

- **高效存储**：存储海量高维向量数据（百万至十亿级）
- **快速检索**：通过ANN（近似最近邻）算法实现毫秒级相似度搜索
- **索引管理**：支持多种索引类型（HNSW、IVF、PQ等）
- **动态更新**：支持文档增删改，保持知识库实时性

#### 4.6 向量数据库类型

| 类型 | 说明 | 代表产品 |
| :--- | :--- | :--- |
| **专用向量数据库** | 原生支持向量存储和检索，性能最优 | Milvus、Pinecone、Weaviate、Qdrant |
| **传统数据库+向量扩展** | 在原有关系型/NoSQL能力上叠加向量功能 | PostgreSQL（pgvector）、Elasticsearch |
| **轻量级嵌入式** | 无服务部署，适合开发测试 | ChromaDB、FAISS（Meta） |

#### 4.7 主流向量数据库功能对比

| 数据库 | 开源 | 分布式 | 云托管 | 索引类型 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Milvus** | ✅ | ✅ | ✅ | IVF、HNSW、PQ等 | **生产级大规模**，企业首选 |
| **Pinecone** | ❌ | ✅ | ✅（全托管）| HNSW | 不想运维，追求快速上线 |
| **Qdrant** | ✅ | ✅ | ✅ | HNSW | 轻量快速，Rust实现 |
| **Weaviate** | ✅ | ✅ | ✅ | HNSW | 内置GraphQL，易用性佳 |
| **ChromaDB** | ✅ | ❌ | ❌ | HNSW | 开发测试、学习原型 |
| **pgvector** | ✅ | ✅ | ❌ | IVFFlat、HNSW | PostgreSQL用户，统一技术栈 |

> **选型建议**：
> - 学习/原型：**ChromaDB**（最简单）
> - 生产/大规模：**Milvus**（功能最全）
> - 云原生/免运维：**Pinecone** 或 **Qdrant Cloud**
> - 已有PostgreSQL：**pgvector**（无需引入新组件）

### 第四阶段：Prompt 上下文增强设计

将检索到的Top-K文档片段，以结构化方式注入到Prompt模板中：

```
## 系统设定
你是一个专业的AI助手，请基于以下参考资料回答用户问题。
如果参考资料中找不到答案，请明确告知用户"未找到相关信息"。

## 参考资料
{retrieved_documents}

## 用户问题
{user_question}

## 回答要求
- 仅基于参考资料回答
- 引用来源时标注出处
- 保持回答简洁、准确
```

**设计要点**：
- **指令明确**：告诉模型“仅基于参考资料回答”，减少幻觉
- **优先级区分**：检索结果按相关度降序排列
- **来源标注**：要求模型在回答中引用来源，增强可信度
- **兜底策略**：当检索结果相关性不足时，明确让模型拒绝回答而非强行编造
